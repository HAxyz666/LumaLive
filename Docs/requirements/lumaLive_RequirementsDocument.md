## 第 0 层　产品定位与业务问题

### 0.1 产品是什么

LumaLive 是一套面向第三方业务的直播能力平台。它以「服务端 API + 三端 SDK + 运营后台」的形态交付，让接入方在自己的 App、H5、小程序里具备开播、播放、互动、录制回放的能力，而不必自建音视频链路。

平台提供四组能力：

| 能力域 | 内容 |
|---|---|
| 接入与房间 | 房间生命周期、鉴权、推流与播放凭证、播放地址签发 |
| 媒体处理与分发 | 推流接入、转码、录制、回放生成、分发编排 |
| 直播间互动 | 弹幕、点赞、举报，以及向接入方业务系统的动作转交 |
| 治理与运营 | 内容送审与人工审核、违规处置、故障处置、租户与配额管理 |

平台不持有内容和流量，也不直接运营终端用户。观众与主播属于接入方，平台负责把内容可靠地送到他们面前，并对交付质量负责。

### 0.2 业务问题

多个业务方都需要向各自的终端用户实时传递现场内容。各自独立建设这套能力，结果是交付质量不可控、投入重复、新场景上线周期长，出故障时也没有明确的责任方。

音视频能力本身已经成熟，问题不在技术可得性。问题在于这是一项非差异化的重投入：单个业务方既建不好，也养不起。再往下追一层——市场上缺少一种可复用、可承诺质量的交付服务，于是每个业务方都在重复解决同一个问题，而这个问题的解法本应只有一份。

### 0.3 现状与目标状态

| | 现状 | 目标 |
|---|---|---|
| 能力来源 | 自建或外包拼装，跨业务线重复建设 | 统一服务，按用量付费 |
| 新场景上线 | 数周至数月，需重新搭建与联调 | 5 个工作日内 |
| 质量责任 | 无明确承诺，故障时各方推诿 | 有 SLA，有明确的故障处置与报告流程 |
| 成本结构 | 固定投入，随业务线增加而重复 | 规模化摊薄，边际成本递减 |

## 第 1 层　目标、范围与涉众

### 1.1 产品目标

让接入方以可预期的成本和可承诺的质量，把现场内容交付给它的终端用户；新增直播场景不再需要重复建设基础设施。

目标对应的各方获益：

- 接入方业务负责人把预算从基础设施转回业务本身，峰值场景的风险可控
- 接入方技术团队不必长期维护音视频链路，接入与排障成本大幅下降
- 观众获得稳定的观看体验，主播获得稳定的开播体验
- 平台通过规模化摊薄单位成本，靠续约与用量增长获得收入

衡量指标：

| 编号 | 指标 | 目标值 |
|---|---|---|
| M1 | 新接入方从签约到首场直播上线 | ≤ 5 个工作日 |
| M2 | 首帧加载时间（P95） | ≤ 1.5 秒 |
| M3 | 播放卡顿率 | ≤ 2% |
| M4 | 端到端延迟（P95，标准档） | ≤ 3 秒 |
| M5 | 直播服务可用性 | ≥ 99.95% |
| M6 | 单位带宽成本较业务方自建 | 下降 ≥ 30% |
| M7 | 接入方续约率 | ≥ 85% |
| M8 | 接入方技术对接满意度 | ≥ 4.2 / 5（季度问卷） |
| M9 | 违规内容从出现到处置完成（P95） | ≤ 60 秒 |

约束条件：

- 分发容量受上游 CDN 的产能与定价约束，M3 与 M5 无法完全由平台单方承诺
- 终端机型与浏览器碎片化，M2、M3 需要降级策略兜底
- V1 须在 9 个月内上线，决定范围裁剪
- 研发总投入有上限，决定自建与采购的分界

### 1.2 范围与外部交互

问题空间是 LumaLive 平台及其三端：观众端、主播端、运营后台。

| 编号 | 方向 | 数据流 |
|---|---|---|
| 1 | 观众 ↔ 平台 | 观看请求；播放流、互动消息与互动下发 |
| 2 | 主播 ↔ 平台 | 开播请求与推流音视频；开播凭证、实时数据 |
| 3 | 接入方业务系统 ↔ 平台 | 房间开通与配置、播放凭证申请；直播事件回调、录制文件索引 |
| 4 | 内容安全服务 ↔ 平台 | 截图与音视频送审；机审结论 |
| 5 | 分发网络 ↔ 平台 | 回源推流；分发质量数据 |
| 6 | 监控告警平台 ↔ 平台 | 质量指标与事件；告警触发 |
| 7 | 运营审核人员 ↔ 平台 | 审核与处置指令；待审队列与实时画面 |
| 8 | 平台管理员 → 平台 | 租户与配额配置、密钥轮换（单向） |
| 9 | 定时任务调度器 → 平台 | 触发定时媒体作业（单向） |
| 10 | 监管机构 → 平台 | 合规要求与报送（约束来源，非业务数据流） |

分发网络、内容安全服务、监控告警平台属于外部依赖。数据库、对象存储、操作系统不作为外部依赖。

### 1.3 改变范围与影响范围

平台可以直接改造的：服务端、三端 SDK、运营后台，以及平台内部的工作流程。

平台只能影响、不能命令的：观众、主播、接入方技术团队。他们必须自愿改变行为，平台无权要求。

平台无法改变的，按约束处理：监管要求、CDN 的产能与定价、接入方自身的业务规则。

### 1.4 范围边界

| V1 覆盖 | V1 不覆盖 |
|---|---|
| 房间与生命周期管理、鉴权与播放凭证 | 接入方自有账号体系与登录 |
| 推流接入、转码、录制、转点播回放 | 交易、支付、订单履约、佣金结算 |
| 播放分发编排与质量自适应 | 自建 CDN 骨干网（采购或租用） |
| 弹幕、点赞、举报等直播间互动 | 全站社交关系链与私信 IM |
| 内容安全送审与人工审核台 | 内容生产工具（剪辑、后期） |
| 租户、配额、巡播、故障处置 | 点播长视频运营 |
| 质量采集、计量数据、告警联动 | 终端推送与短信通道（外部） |

V1 不做，归入后续版本：超低延迟（< 800ms）连麦互动、VR 与全景直播、跨国多区域合规独立部署、虚拟形象动捕。

平台交付直播能力。电商直播场景下，开播与观看由平台提供；商品挂载、下单、支付、履约由接入方系统承担。

### 1.5 用户与涉众

| 角色 | 所属 | 关注点 |
|---|---|---|
| 接入方技术对接人 | 接入方 | 接入快、排障快、错误码与文档清晰 |
| 接入方业务负责人 | 接入方 | 稳定性、成本可预测、出事有人担责 |
| 主播 | 接入方 | 开播稳、不掉线、误判可申诉 |
| 观众 | 接入方 | 秒开、不卡、能互动 |
| 运营与内容审核人员 | 平台 | 及时发现违规与故障、一键处置 |
| 平台管理员 | 平台 | 租户可控、配额可管、密钥可轮换 |
| 值班 SRE | 平台 | 可观测、可降级、可快速止损 |
| 法务合规 | 平台 | 留痕、可追溯、符合监管 |
| CDN 与内容安全服务商 | 外部 | 产能、结算、接口稳定性 |
| 监管机构 | 外部 | 实名、留痕、违规处置、日志留存 |
| 刷量黑产、盗播者 | 外部 | 不会配合，但其滥用路径必须在设计中被考虑 |

付费方是接入方业务负责人，使用方是观众与主播。产品取舍以购买方要求的稳定性、合规与可追责为先，使用体验在其约束内优化。

### 1.6 术语

| 术语 | 定义 |
|---|---|
| 接入方 / 租户 | 与平台建立服务关系、把直播能力嵌入自身业务的组织。一个接入方可有多条业务线。 |
| 直播房间 | 接入方业务中的一个直播位，是权限、审核、录制、回调策略的配置载体。房间不等于一场直播。 |
| 场次 | 从一次成功开播到该次结束的完整过程。一个房间可先后承载多场直播。 |
| 场次标识 | 一场直播的全局唯一标识，是日志、告警、录制、计量的关联主键。 |
| 推流凭证 | 授予主播端向平台推送音视频的有时效凭据。 |
| 播放凭证 | 授予观众端观看某房间的有时效凭据。 |
| 互动消息 | 直播间内的弹幕、点赞、系统提示等非音视频数据，不含接入方自身的交易与订单消息。 |
| 录制 | 直播过程的音视频留存。回放是录制经转码后可直接播放的产物。 |
| 送审 | 将关键帧截图与音视频片段提交内容安全服务进行机器判定。 |
| 风险线索 | 综合机审结论、举报与历史违规记录生成的待人工复核条目。线索不是判定结论。 |
| 处置 | 对风险线索执行的动作：放行、警告、限制分发、中断直播。 |
| 降级 | 部分依赖不可用时，牺牲非核心能力以保住核心能力。此处的核心能力是可观看。 |
| 配额 | 对租户在并发、带宽、存储上的上限约束。 |
| 端到端延迟 | 从主播端采集到观众端渲染的时间差。 |

「房间 / 场次」与「录制 / 回放」在文档、接口字段与沟通过程中严格区分。

## 第 2 层　客户细分、角色原型与优先级

### 2.1 客户细分

细分依据客户要解决的问题，不依据现有系统中的操作任务。

| 编号 | 细分 | 类型 | 要解决的问题 | 关键痛点 |
|---|---|---|---|---|
| **S1** | 接入方技术对接人 | 客户 | 以可预期的工作量，把直播能力嵌进自己的业务 | 文档不全、报错难定位、联调环境不稳定、边界不清 |
| **S2** | 接入方业务负责人 | 客户 | 让直播带来可衡量的业务结果，且风险可控 | 峰值掉链子、成本不可预测、出事找不到人 |
| **S3** | 主播 | 客户（接入方的使用者） | 稳定地把内容传出去，不被误伤 | 掉线、黑屏、音画不同步、被误判违规掐流 |
| **S4** | 观众 | 客户（接入方的使用者） | 点开就能看，能即时参与 | 加载慢、卡顿、费流量、弱网打不开 |
| **S5** | 运营与内容审核人员 | 内部角色 | 在监管与口碑风险发生前发现并处置 | 漏审被通报、误判引发投诉、无一键止损 |
| **S6** | 平台管理员 | 内部角色 | 租户可控、配额可管、密钥可轮换 | 租户越权、配额被刷爆、密钥泄漏难轮换 |
| **S7** | 合规与法务 | 内部角色 | 全程留痕、可追溯、可举证 | 留存不足、处置无记录、跨境数据不合规 |
| **S8** | SRE | 内部角色 | 可观测、可降级、可快速止损 | 定位慢、无降级入口、告警噪音大 |

S1–S4 是客户：他们决定产品该做什么，也决定产品能不能卖出去。S5–S8 是平台自己的角色，诉求进入约束与运营需求，不参与客户价值排序。

### 2.2 角色原型

客户用角色原型描述：以客户群体为抽象实体，以名称代表其特征组合，不设虚构人物。原型只记录影响需求的内容与判断依据。

原型覆盖互相冲突的三类客户：接入方技术对接人、接入方业务负责人、主播。观众的需求由 M2、M3、M4 三个指标约束，不单设原型。S5–S8 是平台内部角色，不参与客户价值排序。

**原型 S1｜接入方技术对接人**

- 要完成的工作：把直播能力接进自家 App 和 H5，不能改动现有登录体系。
- 现在怎么做：对着接口文档写代码。出错先看 HTTP 状态码，没有响应体就去群里问对接人。
- 卡在哪：错误码只有 500 和 400 两种；联调环境每周重置一次；不知道断流事件该在哪个回调里处理。
- 什么情况会放弃：三天调不通，或者每次排查都得找平台的人。
- 会怎么反对：向采购方反馈接入成本过高，续约谈判卡住。
- 依据：接入类产品的公开文档结构与开发者社区的提问模式（团队归纳）。接入期工单量与首次调通耗时，待上线验证。

**原型 S2｜接入方业务负责人（付费方）**

- 要完成的工作：为直播能力签预算，并对大促期间的稳定性负责。
- 现在怎么做：让技术团队评估，自己看同行的事故新闻判断风险。
- 卡在哪：分不清 99.95% 和 99.9% 的实际差别；出故障时不知道该找谁。
- 什么情况会放弃：故障之后拿不到一份能直接交给上级的书面说明。
- 会怎么反对：不续约，或把新业务线切给另一家。
- 依据：公开 SLA 条款与故障公告的通行写法。故障报告的实际使用场景待接入方确认。

**原型 S3｜主播**

- 要完成的工作：一场 3–6 小时的带货直播，手机加补光灯，在家里或档口。
- 现在怎么做：开播前试一下画面，中途靠助手盯弹幕。
- 卡在哪：断流时判断不了是自己网络还是平台；被判定违规掐流后找不到申诉入口。
- 什么情况会放弃：一场直播断两次以上；误判后两天没有回音。
- 会怎么反对：把直播搬到别家，内容供给流失。
- 依据：应用商店评论中反复出现的同类抱怨（团队归纳）。断流归因与申诉时效，待上线数据验证。

### 2.3 客户细分的优先级

按价值排序。价值可以来自当前收入、未来价值，也可以是风险敞口。

| 细分 | 业务价值（收入/续约） | 需求覆盖面 | 风险敞口 | 优先级 |
|---|---|---|---|---|
| S2 接入方业务负责人 | ★★★★★（付费决策） | 低 | 中 | **一级** |
| S1 接入方技术对接人 | ★★★★☆（守门人） | 低 | 高（接不进等于不签约） | **一级** |
| S4 观众 | ★★★★☆（规模决定接入方业务结果） | 极高 | 中 | **一级** |
| S3 主播 | ★★★☆☆（内容供给） | 中 | 高（无内容则无观众） | 二级 |
| S5 运营与内容审核 | ★★☆☆☆ | 低 | ★★★★★（合规一票否决） | 二级（风险维度置顶） |
| S6 平台管理员 | ★★☆☆☆ | 低 | 中高 | 三级 |
| S8 SRE | ★★☆☆☆ | 低 | 高 | 三级 |
| S7 合规与法务 | ★☆☆☆☆ | 低 | 高（约束型，必须满足） | 三级（不做价值排序） |

战略转向中小客户自助接入时，排序依据由当前收入改为期望价值，S1 提到第一位。该决策由管理层作出。

## 第 3 层　业务事件与增量划分

### 3.1 业务事件
3333
业务事件是外部触发与平台响应的对应单元。外部事件由参与者发起，时间事件由计划触发，条件事件由状态跃迁触发。

增量按业务事件划分。事件清单覆盖平台与外界交换的全部数据，含无用户参与的定时与阈值触发事件。

### 3.2 三类业务事件

| 类型 | 定义 | 本项目的典型来源 |
|---|---|---|

时间与条件触发事件的发起者建模为定时任务调度器。

### 4.1 系统边界的确定

**系统之内**：接入网关与服务端 API、客户端 SDK（观众端/主播端）、房间与生命周期服务、媒体处理与分发编排、互动消息服务、录制与回放服务、运营后台、质量与计量采集。

| 主播的摄像头、麦克风、手机 | **设备不是参与者**，用它们的**主播**才是 |

### 4.4 用况粒度判别记录

这是本层最容易出错的地方，显式记录判据：

1. **为什么"发弹幕"不单独成用况？** 离开"观看"单独发弹幕对观众没有价值。因此弹幕/点赞/业务跳转作为 UC-01 的基本流/备选流——独立出来就是**功能分解**（"环状马车"）。
2. **为什么"开始直播/结束直播"不拆成两个用况？** 单独"结束"离开"开播"也无价值。主播真正的目标是"**做完一场直播**"，故合并为 UC-03。
3. **为什么"举报"可以独立？** 举报有**独立价值**：即使观众不观看，仅举报一条违规内容也能产生治理与合规价值，且是监管要求。

**用况独立性声明**：本模型 9 个用况**彼此独立、互不调用、互不依赖**。跨用况的公共行为（鉴权、留痕）不建模为 `<<include>>`，而作为**子流**在被需要的用况内部展开，或作为**补充需求**在第 6 层统一说明。

### 4.5 追踪检查

- 每个客户细分（S1–S8）**至少**被一个参与者覆盖
- 每个参与者**至少**参与一个用况（无冗余参与者）
- 每个涉众的利益**至少**在某个用况中被表达：接入方业务负责人（S2）→ UC-05、UC-09；合规与法务（S7）→ UC-02、UC-06；SRE（S8）→ UC-07
- 21 个业务事件全部被 9 个用况覆盖，无事件悬空

## 第 5 层　用况详细规约

### 5.0 模板与填写规则

模板依据 `withdraw_cash_use-case_spec`（Bittner & Spence），本版略去备选流段：

`简要描述 → 前置条件 → 基本流 → 子流 → 关键场景 → 后置条件 → 扩展点 → 特殊需求`

编号约定：基本流 `B.x`；子流 `S.x`。

三条填写规则：

1. **基本流只写"必须发生的事"**，不写界面操作与内部实现。
2. **后置条件必须覆盖全部退出路径**（成功 / 失败 / 未启动 / 部分完成），不能只写成功路径。
3. **特殊需求必须可度量**；不可度量的写进"待确认"，不要写"尽量快"。

### 5.1 UC-04　开通并配置直播房间

**版本** v1.0　**参与者** 接入方集成系统（主）

#### 1. 简要描述
本用况描述接入方如何创建直播房间、配置鉴权与治理策略、并取得推流与播放凭证。为**接入方技术对接人**提供的价值是：无需理解音视频细节即可具备开播能力；为**接入方业务负责人**提供的价值是：直播能力可以在 5 个工作日内上线，而不是数周。

#### 2. 前置条件
- 该租户已开通且处于可用状态（**所需前条件**）
- 接入方持有有效的租户凭据（**所需前条件**）
- 该租户的房间配额未用尽（**所需前条件**）
- 接入方的回调接收端已就绪（**假设 ASM-1**）

#### 3. 基本流

| 步骤 | 动作 |
|---|---|
| **B.1 发起开通** | 接入方携带租户凭据调用开通接口，并在请求中给出**业务侧房间标识**（接入方自己的房间号）。 |
| **B.2 校验** | 系统校验租户状态、凭据有效性、房间配额与权限。 |
| **B.3 创建房间** | 系统创建房间实体，建立"业务侧房间标识 ↔ 平台房间标识"的映射，并返回平台房间标识。 |
| **B.4 提交策略** | 接入方提交策略配置：鉴权方式、审核策略、录制开关、回调地址。 |
| **B.5 策略校验** | 系统执行子流 **S.1 策略合法性校验**。 |
| **B.6 签发凭证** | 系统签发推流凭证与播放凭证，两者均带有效期与作用域。 |
| **B.7 返回自检清单** | 系统返回房间标识、凭证、以及**接入自检清单**（调用方可据此逐项确认接入是否完整）。 |
| **B.8 用况结束** | 用况结束。 |

#### 4. 子流

**S.1 策略合法性校验**
1. 校验鉴权方式是否在该租户的可选范围内。
2. 校验审核策略与业务类型是否匹配（例如强互动场景不允许关闭送审）。
3. 校验回调地址的协议、格式与可达性。
4. 校验录制开关与存储配额是否相容。
5. 校验策略组合之间是否存在冲突（如"关闭送审"与"必须留痕"同时成立）。

#### 5. 关键场景
- **成功**：首次开通并一次校验通过（基本流）。
- **失败**：本版未展开.

#### 6. 后置条件
- 房间已创建且策略已生效，凭证已签发，接入方已获得自检清单。
- **或**：房间未创建，未占用配额，接入方已获知明确原因与处理建议。
- **或**：房间已存在于前次调用（幂等），本次未产生新增资源。
- 无论何种路径：**凭证不得以明文形式出现在任何日志中**。

#### 7. 扩展点
无。

#### 8. 特殊需求

| ID | 需求 |
|---|---|
| SR-UC04-1 | 开通接口必须**幂等**：相同业务侧房间标识的重复调用不得产生重复资源。 |
| SR-UC04-2 | 所有错误响应必须包含**结构化错误码 + 人话解释 + 处理建议**三项（接入方技术对接人的音视频领域知识接近于零）。 |
| SR-UC04-3 | 凭证必须带有效期且可**单独轮换**，轮换不得中断进行中的直播。 |
| SR-UC04-4 | 从签约到首场直播上线 ≤ 5 个工作日（M1）；自检清单须覆盖全部必做接入步骤。 |

### 5.2 UC-05　接收直播事件通知

**版本** v1.0　**参与者** 接入方集成系统（支持）　**发起方** 中台（系统发起）

#### 1. 简要描述
本用况描述中台如何在直播状态发生变化的时刻，**主动**把事件推送给接入方业务系统。为**接入方**提供的价值是：其业务系统能与直播状态保持同步，而不必轮询；为**接入方业务负责人**提供的价值是：营销、客服、履约等下游动作可以建立在准确的直播状态之上。

这是**由系统发起**的用况——关联箭头方向从用况指向参与者，与其余用况相反（RE 04 §"关联用况到参与者"）。

#### 2. 前置条件
- 该房间已配置有效的回调地址（**所需前条件**）
- 事件已在中台内部产生（**领域前条件**）
- 接入方回调接收端可接受公网请求（**假设 ASM-1**）

#### 3. 基本流

| 步骤 | 动作 |
|---|---|
| **B.1 事件产生** | 中台内部产生一条领域事件（开播/断流/恢复/结束/违规处置/录制完成）。 |
| **B.2 组装载荷** | 系统组装事件载荷：事件类型、房间标识、场次标识、发生时间、事件序号、业务扩展字段。 |
| **B.3 签名** | 系统对载荷计算签名，附于请求头，供接收方验证来源与完整性。 |
| **B.4 投递** | 系统按事件类型对应的回调地址投递请求。 |
| **B.5 接收确认** | 接入方在约定超时内返回成功应答。 |
| **B.6 记录投递结果** | 系统记录投递时间、耗时、响应码，并标记该事件为"已送达"。 |
| **B.7 用况结束** | 用况结束。 |

#### 4. 子流
无（本用况以顺序流程为主，复用的重试与签名逻辑直接内联，避免为两个用况抽公共子流造成耦合）。

#### 5. 关键场景
- **成功**：事件即时送达（基本流）。
- **失败**：本版未展开.

#### 6. 后置条件
- 事件已送达且被接收方确认，投递结果已记录。
- **或**：事件已进入死信队列，接入方与值班运营已获通知。
- **或**：事件被记录但未投递（未订阅），可供后续补投。
- 无论何种路径：**同一场次的事件在接入方侧可按事件序号重建完整时序**。

#### 7. 扩展点
无。

#### 8. 特殊需求

| ID | 需求 |
|---|---|
| SR-UC05-1 | 投递语义为**至少一次**；每条事件带全局唯一序号，接收方可据此幂等。 |
| SR-UC05-2 | 事件下发时延 P95 ≤ 3 秒。 |
| SR-UC05-3 | 同一房间的事件**不得乱序**；允许延迟，不允许颠倒。 |
| SR-UC05-4 | 投递请求必须带签名，接收方可验证来源与载荷完整性。 |
| SR-UC05-5 | 死信事件至少保留 7 天可供补投与审计。 |

### 5.3 UC-03　进行一场直播

**版本** v1.0　**参与者** 主播（主）、分发网络（支持）

#### 1. 简要描述
本用况描述主播如何从开播前自检开始，取得推流凭证、开始推流、在直播过程中进行管控，直到结束直播并产出可回放的录制资产。为**主播**提供的价值是：把一场直播稳定、完整地做完，结束时立刻拥有可用回放；为**接入方**提供的价值是：直播状态可被其业务系统感知（经 UC-05），录制资产可被复用。

#### 2. 前置条件
- 主播已由接入方完成身份绑定，且对目标房间具备开播权限（**所需前条件**）
- 目标房间已通过 UC-04 开通，处于"未开播"状态（**领域前条件**）
- 主播端与中台网络可达（**假设**）
- 中台与分发网络链路健康（**假设**）
- 该租户并发配额未用尽（**所需前条件**）

#### 3. 基本流

| 步骤 | 动作 |
|---|---|
| **B.1 发起开播** | 主播选择目标房间并点击"开始直播"。系统分配**全局唯一的场次标识**，用于后续日志、告警与录制资产的关联。 |
| **B.2 开播前自检** | 系统执行子流 **S.1 开播环境与网络自检**，并以**非技术语言**展示结论与建议。 |
| **B.3 取得推流凭证** | 系统下发**有时效的推流地址与凭证**（含推荐码率与分辨率档位）。 |
| **B.4 开始推流** | 主播端开始推送音视频。系统检测到首个关键帧后，将房间状态置为"直播中"。 |
| **B.5 发布开播状态** | 系统生成播放地址并触发"开播"事件（由 UC-05 投递给接入方）。此处仅为**事件触发**，不构成用况调用。 |
| **B.6 建立分发** | 系统将流推至分发网络，完成回源与边缘分发编排。 |
| **B.7 过程监控与管控** | 直播进行中，系统持续采集质量指标并向主播展示实时数据。主播可执行过程管控。 |
| **B.8 结束直播** | 主播点击"结束直播"。系统停止接收推流，房间状态置为"已结束"。 |
| **B.9 产出录制** | 若该房间开启录制，系统执行子流 **S.2 生成录制与回放**；否则跳过。 |
| **B.10 释放与结算** | 系统释放推流凭证与并发配额，记录计量数据，并触发"结束"与"录制完成"事件。 |
| **B.11 用况结束** | 用况结束。 |

#### 4. 子流

**S.1 开播环境与网络自检**
1. 检测上行带宽、丢包率、设备编码能力、麦克风与摄像头可用性。
2. 依据结果推荐码率与分辨率档位（而非让主播自选技术参数）。
3. 将结论翻译为**非技术语言**展示，并标注"建议"与"最低要求"两级阈值。

**S.2 生成录制与回放**
1. 直播结束后（或按配置分段）整理录制片段。
2. 执行转码，生成标准回放格式，并生成关键帧截图作为封面候选。
3. 写入录制文件索引，并触发"录制完成"事件。
4. 失败则记录事件、通知运营与接入方，并保留原始片段以便重试。

**S.3 异常结束直播**
1. 房间状态置为"已结束"，并标记结束原因（超时中断 / 违规中断 / 系统异常）。
2. 释放推流凭证与并发配额。
3. 按接入方配置决定是否产出录制。
4. 触发"结束"事件（含结束原因）。

#### 5. 关键场景
**成功**：正常开播并正常结束（基本流）；开启录制后回放可用（+S.2）。
**失败**：本版未展开.

#### 6. 后置条件
- 系统已正常结束一场直播，房间回到"未开播"，录制资产（若开启）已生成且索引可被接入方访问。
- **或**：已异常结束，结束原因已记录，资源已释放，接入方已获通知。
- **或**：开播未建立，未产生任何对外分发与计费记录，已分配资源已回收。
- 无论何种结束方式：**该场直播全过程（含每次断流、降级、处置）均已留痕，可按场次标识完整追溯**。

#### 7. 扩展点
无。

#### 8. 特殊需求

| ID | 需求 |
|---|---|
| SR-UC03-1 | 从点击"开始直播"到观众侧出现首帧，P95 ≤ 3 秒。 |
| SR-UC03-2 | 推流中断后在自动恢复窗口内的重连成功率 ≥ 95%。 |
| SR-UC03-3 | 任一场直播的**每一次状态变更**都必须写入事件日志并可在 5 分钟内被检索。 |
| SR-UC03-4 | 开播自检的展示文案**不得出现**码率、分辨率、GOP、帧率等技术术语。 |
| SR-UC03-5 | 违规中断后，系统必须向主播同步**申诉入口**与**申诉响应时限承诺**。 |
