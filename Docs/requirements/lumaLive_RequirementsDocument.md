## 第 0 层　产品定位与业务问题

### 0.1 产品是什么

LumaLive 是一套面向第三方业务的直播能力平台。它以「服务端 API + 三端 SDK + 运营后台」的形态交付，让接入方在自己的 App、H5、小程序里具备开播、播放、互动、录制回放的能力，而不必自建音视频链路。

平台提供四组能力：

| 能力域 | 内容 |
|---|---|
| 接入与房间 | 房间生命周期、鉴权、推流与播放凭证、播放地址签发 |
| 媒体处理与分发 | 推流接入、转码、录制、回放生成、分发编排 |
| 直播间互动 | 弹幕、点赞、举报，以及向接入方业务系统的动作转交 |
| 治理与运营 | 内容送审与人工审核、违规处置、故障处置、租户与配额管理 |

平台不持有内容和流量，也不直接运营终端用户。观众与主播属于接入方，平台负责把内容可靠地送到他们面前，并对交付质量负责。

### 0.2 业务问题

多个业务方都需要向各自的终端用户实时传递现场内容。各自独立建设这套能力，结果是交付质量不可控、投入重复、新场景上线周期长，出故障时也没有明确的责任方。

音视频能力本身已经成熟，问题不在技术可得性。问题在于这是一项非差异化的重投入：单个业务方既建不好，也养不起。再往下追一层——市场上缺少一种可复用、可承诺质量的交付服务，于是每个业务方都在重复解决同一个问题，而这个问题的解法本应只有一份。

### 0.3 现状与目标状态

| | 现状 | 目标 |
|---|---|---|
| 能力来源 | 自建或外包拼装，跨业务线重复建设 | 统一服务，按用量付费 |
| 新场景上线 | 数周至数月，需重新搭建与联调 | 5 个工作日内 |
| 质量责任 | 无明确承诺，故障时各方推诿 | 有 SLA，有明确的故障处置与报告流程 |
| 成本结构 | 固定投入，随业务线增加而重复 | 规模化摊薄，边际成本递减 |

## 第 1 层　目标、范围与涉众

### 1.1 产品目标

让接入方以可预期的成本和可承诺的质量，把现场内容交付给它的终端用户；新增直播场景不再需要重复建设基础设施。

目标对应的各方获益：

- 接入方业务负责人把预算从基础设施转回业务本身，峰值场景的风险可控
- 接入方技术团队不必长期维护音视频链路，接入与排障成本大幅下降
- 观众获得稳定的观看体验，主播获得稳定的开播体验
- 平台通过规模化摊薄单位成本，靠续约与用量增长获得收入

衡量指标：

| 编号 | 指标 | 目标值 |
|---|---|---|
| M1 | 新接入方从签约到首场直播上线 | ≤ 5 个工作日 |
| M2 | 首帧加载时间（P95） | ≤ 1.5 秒 |
| M3 | 播放卡顿率 | ≤ 2% |
| M4 | 端到端延迟（P95，标准档） | ≤ 3 秒 |
| M5 | 直播服务可用性 | ≥ 99.95% |
| M6 | 单位带宽成本较业务方自建 | 下降 ≥ 30% |
| M7 | 接入方续约率 | ≥ 85% |
| M8 | 接入方技术对接满意度 | ≥ 4.2 / 5（季度问卷） |
| M9 | 违规内容从出现到处置完成（P95） | ≤ 60 秒 |

约束条件：

- 分发容量受上游 CDN 的产能与定价约束，M3 与 M5 无法完全由平台单方承诺
- 终端机型与浏览器碎片化，M2、M3 需要降级策略兜底
- V1 须在 9 个月内上线，决定范围裁剪
- 研发总投入有上限，决定自建与采购的分界

### 1.2 范围与外部交互

问题空间是 LumaLive 平台及其三端：观众端、主播端、运营后台。

| 编号 | 方向 | 数据流 |
|---|---|---|
| 1 | 观众 ↔ 平台 | 观看请求；播放流、互动消息与互动下发 |
| 2 | 主播 ↔ 平台 | 开播请求与推流音视频；开播凭证、实时数据 |
| 3 | 接入方业务系统 ↔ 平台 | 房间开通与配置、播放凭证申请；直播事件回调、录制文件索引 |
| 4 | 内容安全服务 ↔ 平台 | 截图与音视频送审；机审结论 |
| 5 | 分发网络 ↔ 平台 | 回源推流；分发质量数据 |
| 6 | 监控告警平台 ↔ 平台 | 质量指标与事件；告警触发 |
| 7 | 运营审核人员 ↔ 平台 | 审核与处置指令；待审队列与实时画面 |
| 8 | 平台管理员 → 平台 | 租户与配额配置、密钥轮换（单向） |
| 9 | 定时任务调度器 → 平台 | 触发定时媒体作业（单向） |
| 10 | 监管机构 → 平台 | 合规要求与报送（约束来源，非业务数据流） |

分发网络、内容安全服务、监控告警平台属于外部依赖。数据库、对象存储、操作系统不作为外部依赖。

### 1.3 改变范围与影响范围

平台可以直接改造的：服务端、三端 SDK、运营后台，以及平台内部的工作流程。

平台只能影响、不能命令的：观众、主播、接入方技术团队。他们必须自愿改变行为，平台无权要求。

平台无法改变的，按约束处理：监管要求、CDN 的产能与定价、接入方自身的业务规则。

### 1.4 范围边界

| V1 覆盖 | V1 不覆盖 |
|---|---|
| 房间与生命周期管理、鉴权与播放凭证 | 接入方自有账号体系与登录 |
| 推流接入、转码、录制、转点播回放 | 交易、支付、订单履约、佣金结算 |
| 播放分发编排与质量自适应 | 自建 CDN 骨干网（采购或租用） |
| 弹幕、点赞、举报等直播间互动 | 全站社交关系链与私信 IM |
| 内容安全送审与人工审核台 | 内容生产工具（剪辑、后期） |
| 租户、配额、巡播、故障处置 | 点播长视频运营 |
| 质量采集、计量数据、告警联动 | 终端推送与短信通道（外部） |

V1 不做，归入后续版本：超低延迟（< 800ms）连麦互动、VR 与全景直播、跨国多区域合规独立部署、虚拟形象动捕。

平台交付直播能力。电商直播场景下，开播与观看由平台提供；商品挂载、下单、支付、履约由接入方系统承担。

### 1.5 用户与涉众

| 角色 | 所属 | 关注点 |
|---|---|---|
| 接入方技术对接人 | 接入方 | 接入快、排障快、错误码与文档清晰 |
| 接入方业务负责人 | 接入方 | 稳定性、成本可预测、出事有人担责 |
| 主播 | 接入方 | 开播稳、不掉线、误判可申诉 |
| 观众 | 接入方 | 秒开、不卡、能互动 |
| 运营与内容审核人员 | 平台 | 及时发现违规与故障、一键处置 |
| 平台管理员 | 平台 | 租户可控、配额可管、密钥可轮换 |
| 值班 SRE | 平台 | 可观测、可降级、可快速止损 |
| 法务合规 | 平台 | 留痕、可追溯、符合监管 |
| CDN 与内容安全服务商 | 外部 | 产能、结算、接口稳定性 |
| 监管机构 | 外部 | 实名、留痕、违规处置、日志留存 |
| 刷量黑产、盗播者 | 外部 | 不会配合，但其滥用路径必须在设计中被考虑 |

付费方是接入方业务负责人，使用方是观众与主播。产品取舍以购买方要求的稳定性、合规与可追责为先，使用体验在其约束内优化。

### 1.6 术语

| 术语 | 定义 |
|---|---|
| 接入方 / 租户 | 与平台建立服务关系、把直播能力嵌入自身业务的组织。一个接入方可有多条业务线。 |
| 直播房间 | 接入方业务中的一个直播位，是权限、审核、录制、回调策略的配置载体。房间不等于一场直播。 |
| 场次 | 从一次成功开播到该次结束的完整过程。一个房间可先后承载多场直播。 |
| 场次标识 | 一场直播的全局唯一标识，是日志、告警、录制、计量的关联主键。 |
| 推流凭证 | 授予主播端向平台推送音视频的有时效凭据。 |
| 播放凭证 | 授予观众端观看某房间的有时效凭据。 |
| 互动消息 | 直播间内的弹幕、点赞、系统提示等非音视频数据，不含接入方自身的交易与订单消息。 |
| 录制 | 直播过程的音视频留存。回放是录制经转码后可直接播放的产物。 |
| 送审 | 将关键帧截图与音视频片段提交内容安全服务进行机器判定。 |
| 风险线索 | 综合机审结论、举报与历史违规记录生成的待人工复核条目。线索不是判定结论。 |
| 处置 | 对风险线索执行的动作：放行、警告、限制分发、中断直播。 |
| 降级 | 部分依赖不可用时，牺牲非核心能力以保住核心能力。此处的核心能力是可观看。 |
| 配额 | 对租户在并发、带宽、存储上的上限约束。 |
| 端到端延迟 | 从主播端采集到观众端渲染的时间差。 |

「房间 / 场次」与「录制 / 回放」在文档、接口字段与沟通过程中严格区分。

## 第 2 层　客户细分、角色原型与优先级

### 2.1 客户细分

细分依据客户要解决的问题，不依据现有系统中的操作任务。

| 编号 | 细分 | 类型 | 要解决的问题 | 关键痛点 |
|---|---|---|---|---|
| **S1** | 接入方技术对接人 | 客户 | 以可预期的工作量，把直播能力嵌进自己的业务 | 文档不全、报错难定位、联调环境不稳定、边界不清 |
| **S2** | 接入方业务负责人 | 客户 | 让直播带来可衡量的业务结果，且风险可控 | 峰值掉链子、成本不可预测、出事找不到人 |
| **S3** | 主播 | 客户（接入方的使用者） | 稳定地把内容传出去，不被误伤 | 掉线、黑屏、音画不同步、被误判违规掐流 |
| **S4** | 观众 | 客户（接入方的使用者） | 点开就能看，能即时参与 | 加载慢、卡顿、费流量、弱网打不开 |
| **S5** | 运营与内容审核人员 | 内部角色 | 在监管与口碑风险发生前发现并处置 | 漏审被通报、误判引发投诉、无一键止损 |
| **S6** | 平台管理员 | 内部角色 | 租户可控、配额可管、密钥可轮换 | 租户越权、配额被刷爆、密钥泄漏难轮换 |
| **S7** | 合规与法务 | 内部角色 | 全程留痕、可追溯、可举证 | 留存不足、处置无记录、跨境数据不合规 |
| **S8** | SRE | 内部角色 | 可观测、可降级、可快速止损 | 定位慢、无降级入口、告警噪音大 |

S1–S4 是客户：他们决定产品该做什么，也决定产品能不能卖出去。S5–S8 是平台自己的角色，诉求进入约束与运营需求，不参与客户价值排序。

### 2.2 角色原型

客户用角色原型描述：以客户群体为抽象实体，以名称代表其特征组合，不设虚构人物。原型只记录影响需求的内容与判断依据。

原型覆盖互相冲突的三类客户：接入方技术对接人、接入方业务负责人、主播。观众的需求由 M2、M3、M4 三个指标约束，不单设原型。S5–S8 是平台内部角色，不参与客户价值排序。

**原型 S1｜接入方技术对接人**

- 要完成的工作：把直播能力接进自家 App 和 H5，不能改动现有登录体系。
- 现在怎么做：对着接口文档写代码。出错先看 HTTP 状态码，没有响应体就去群里问对接人。
- 卡在哪：错误码只有 500 和 400 两种；联调环境每周重置一次；不知道断流事件该在哪个回调里处理。
- 什么情况会放弃：三天调不通，或者每次排查都得找平台的人。
- 会怎么反对：向采购方反馈接入成本过高，续约谈判卡住。
- 依据：接入类产品的公开文档结构与开发者社区的提问模式（团队归纳）。接入期工单量与首次调通耗时，待上线验证。

**原型 S2｜接入方业务负责人（付费方）**

- 要完成的工作：为直播能力签预算，并对大促期间的稳定性负责。
- 现在怎么做：让技术团队评估，自己看同行的事故新闻判断风险。
- 卡在哪：分不清 99.95% 和 99.9% 的实际差别；出故障时不知道该找谁。
- 什么情况会放弃：故障之后拿不到一份能直接交给上级的书面说明。
- 会怎么反对：不续约，或把新业务线切给另一家。
- 依据：公开 SLA 条款与故障公告的通行写法。故障报告的实际使用场景待接入方确认。

**原型 S3｜主播**

- 要完成的工作：一场 3–6 小时的带货直播，手机加补光灯，在家里或档口。
- 现在怎么做：开播前试一下画面，中途靠助手盯弹幕。
- 卡在哪：断流时判断不了是自己网络还是平台；被判定违规掐流后找不到申诉入口。
- 什么情况会放弃：一场直播断两次以上；误判后两天没有回音。
- 会怎么反对：把直播搬到别家，内容供给流失。
- 依据：应用商店评论中反复出现的同类抱怨（团队归纳）。断流归因与申诉时效，待上线数据验证。

### 2.3 客户细分的优先级

按价值排序。价值可以来自当前收入、未来价值，也可以是风险敞口。

| 细分 | 业务价值（收入/续约） | 需求覆盖面 | 风险敞口 | 优先级 |
|---|---|---|---|---|
| S2 接入方业务负责人 | ★★★★★（付费决策） | 低 | 中 | **一级** |
| S1 接入方技术对接人 | ★★★★☆（守门人） | 低 | 高（接不进等于不签约） | **一级** |
| S4 观众 | ★★★★☆（规模决定接入方业务结果） | 极高 | 中 | **一级** |
| S3 主播 | ★★★☆☆（内容供给） | 中 | 高（无内容则无观众） | 二级 |

## 第 3 层　业务事件与增量划分

### 3.1 业务事件

业务事件是外部触发与平台响应的对应单元。外部事件由参与者发起，时间事件由计划触发，条件事件由状态跃迁触发。

增量按业务事件划分。事件清单覆盖平台与外界交换的全部数据，含无用户参与的定时与阈值触发事件。

### 3.2 三类业务事件

| 类型 | 定义 | 本项目的典型来源 |
|---|---|---|
| **外部事件** | 系统外部的参与者主动采取行动并告知系统 | 接入方调用、主播开播、观众进入、内容安全服务回结论 |
| **时间触发事件** | 到某个时点，业务必须自己发起工作 | 转码、抽帧送审、录制清理、计量归档、凭证回收 |
| **条件触发事件** | 某个状态量越过了阈值 | 举报激增、配额逼近、在线骤降、连续失败 |

时间与条件触发事件的发起者建模为定时任务调度器。

### 3.4 数据守恒检查（RE 02 §7.2.4）

对每条业务事件检查"输入数据是否足以支撑响应、输出数据是否有去处"：

| 检查项 | 结论 |
|---|---|
| 10 条数据流是否都有事件承接 | 全部承接。其中数据流 8（管理员配置）由 EVT-01 与 EVT-19 共同承接 |
| 是否存在有输出无消费者的数据 | 无。录制索引的投递由 EVT-13 按接入方配置决定，未订阅时不产生投递，并记为假设 ASM-1 |
| 是否存在有响应无输入的工作 | 无。凭证回收由 EVT-17 作为时间触发事件发起 |
| 时间与条件触发事件是否被遗漏 | 时间触发 5 个、条件触发 4 个，已单列 |

无发起人的工作不进入事件清单。

### 3.5 增量划分

依据：**业务事件完整性 × 客户细分优先级 × 风险**。一个增量必须能独立交付可感知的价值。

| 增量 | 主题 | 覆盖业务事件 | 交付价值（可被谁感知） | 预计覆盖用况（待第 4 层确认） |
|---|---|---|---|---|
| **I1** | 接入与开播闭环 | EVT-01、02、03、04、05、17 | 接入方能开通房间并完成一场直播、能收到状态事件——**最小可签约能力**（S1、S2 可感知） | UC-04、UC-05、UC-03 |
| **I2** | 观看与互动 | EVT-06、07、08、09、10、18 | 观众能秒开、能互动、能举报——**业务价值兑现**（S4 可感知） | UC-01、UC-02 |
| **I3** | 治理与运营 | EVT-12、13、14、15、16、19、20、21 | 能过审、能止损、能对账、能管租户——**上得了线、扛得住风险**（S5、S7、S8 可感知） | UC-06、UC-07、UC-08、UC-09 |

I3 覆盖事件最多。EVT-19/20/21 的埋点可提前至 I1，处置能力作为整体在 I3 交付。

增量按业务事件划分，不按技术模块划分。
